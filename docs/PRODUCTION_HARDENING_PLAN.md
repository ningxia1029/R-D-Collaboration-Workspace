# 工作台阶段 0–5 优化与交付方案

## 目标与原则

在不破坏现有业务数据和用户脏工作树的前提下，把“功能可演示”推进到“可审计、可迁移、可验证、可发布”。所有数据库变更先生成迁移与恢复方案，不直接操作现有数据库；外部发布和生产配置变更需单独授权。

## 阶段执行结果

| 阶段 | 本轮结果 | 验收边界 |
|---|---|---|
| 0 基线 | 建立隔离分支，复核根目录交付报告、Git 状态、类型检查、依赖审计和发布资产 | 原有 `.workbuddy`、提交说明改动未覆盖 |
| 1 安全 | 统一实体项目归属校验；修复文档/评论/批量任务/依赖/工时/搜索越权；移除桌面密钥；更新包 SHA-256 校验；收紧 XSS、错误与安全响应头 | 仍需网关级限流、CSRF 策略和依赖漏洞处置 |
| 2 数据可靠性 | PostgreSQL 基线迁移、常用索引、备份/恢复脚本；ECR/ECO 状态、审批和审计纳入事务 | 未连接现有数据库，迁移与恢复需隔离环境演练 |
| 3 业务闭环 | 任务工时、依赖查看/删除、实体选择式追溯；ECO 影响项输入和审批历史；修正 BOM 自动阻塞关联与恢复 | 未完成真实浏览器角色矩阵与大数据量性能验收 |
| 4 工程化 | Node 测试、Windows CI、Dependabot、固定资产名、校验清单随 Release 上传 | 当前测试覆盖仍偏低，需继续补 API 集成和 E2E |
| 5 验证交付 | 类型、Prisma、脚本语法、单元测试和生产构建已执行；报告与验收清单更新 | 依赖漏洞、数据库演练、桌面真机与正式发布仍阻断生产验收 |

## 后续优先级

1. P0：处置 `npm audit` 的 2 严重/4 高危依赖；SheetJS 建议替换为有安全维护版本的解析库，并对上传大小/行列数设限。
2. P0：在隔离 PostgreSQL 恢复库验证 baseline resolve、索引迁移、备份校验和恢复抽样。
3. P0：完成 admin/pm/engineer/viewer × 项目成员/非成员的 API 与 GUI 越权矩阵。
4. P1：把登录限流迁移到 Redis/网关；形成明确的 SameSite/CSRF 方案；为 API 增加统一 Zod schema。
5. P1：增加 Playwright 关键路径与桌面真机更新验收，覆盖断网、哈希不匹配、回滚和旧包保留。

## 回滚

- 代码：当前变更位于 `codex/workbuddy-production-hardening`，未提交、未推送，可逐文件审阅。
- 数据：本轮未执行迁移；正式部署前先备份，再按迁移批次部署。索引迁移可在回滚 SQL 中逐项 `DROP INDEX`。
- 桌面：保留旧安装包；新包下载后不自动覆盖当前外壳，更新失败可继续运行旧版本。
